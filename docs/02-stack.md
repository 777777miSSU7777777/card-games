## 1. Принципы

1. **Минимум технологий.** Каждая зависимость должна окупаться. Нет Redis, нет брокера, нет Kubernetes — только то, что нужно для 5 столов.
2. **Один язык программирования.** TypeScript на сервере, web и mobile: общие типы протокола, движки правил и Redux-слой.
3. **Библиотеки, а не самодельная инфраструктура.** Mantine вместо собственной дизайн-системы, Redux Toolkit вместо набора мелких сторов, Drizzle вместо ручного SQL-слоя.
4. **LTS и предсказуемость.** Node.js 26 LTS, PostgreSQL 18, стабильные версии библиотек; обновления — по необходимости.
5. **Простое развёртывание.** Один Docker Compose (app + postgres) на любой машине; хостинг — позже.

## 3. Ключевые решения

### ADR-001. TypeScript на всём стеке

**Решение.** Один язык: сервер, web, mobile, движки правил.
**Почему.** Правила и протокол описываются один раз в `packages/domain` и `packages/protocol`; клиенты не дублируют типы; команда из 3–4 человек не переключает контекст.
**Альтернативы.** Go/Rust — избыточны для 5 столов и потребуют дублировать правила; .NET — меньше общий рынок с web/mobile; Elixir — неоправданный найм.
**Цена.** CPU-тяжёлых задач нет; если появятся (например, массовые симуляции), выносятся отдельно без смены языка.

### ADR-002. Один процесс вместо нескольких сервисов

**Решение.** HTTP + WebSocket + статика + таймеры в одном NestJS-процессе; одна БД.
**Почему.** Расчёт раздачи и движение фишек должны быть согласованы; в одном процессе это одна транзакция. Нет сетевых хопов, нет деплоя 5 сервисов, нет очередей.
**Альтернативы.** Микросервисы, отдельный realtime-сервис, отдельный воркер — не нужны при 5 столах.
**Когда пересмотреть.** Публичный доступ или 200+ одновременных игроков.

### ADR-003. Собственный простой runtime вместо Colyseus

**Решение.** Реестр столов `Map`, актор на стол, `seq`, проекции, таймеры.
**Почему.** Нужны полный контроль над скрытыми картами, реплеем и расчётом фишек. Colyseus 0.17 — хорошая штука для комнат, но под нас всё равно пришлось бы дописывать проекции и персистентность.
**Цена.** ~1.5–2 тыс. строк своего кода. Для одной игры это окупается уже на первом столе.
**Альтернатива.** Colyseus — только если понадобятся быстрые прототипы новых режимов.

### ADR-004. PostgreSQL — единственное хранилище

**Решение.** Никакого Redis и NATS: состояние столов в памяти, сессии в JWT, чат и история — в PostgreSQL.
**Почему.** Один инстанс, отсутствие распределённых сценариев, минимум эксплуатации. Всё, что «нужен Redis», решается `Map` в памяти.
**Когда пересмотреть.** Второй инстанс приложения → нужен общий presence/кэш; турниры/рассылки → нужен брокер.

### ADR-005. Mantine + Redux Toolkit вместо shadcn/Tailwind + Zustand

**Решение.** Mantine 9 для UI, Redux Toolkit (+ RTK Query) для состояния.
**Почему.**
- Mantine даёт готовые компоненты «из коробки»: формы, модалки, уведомления, меню, таблицы, темы, `@mantine/hooks`. Меньше собственного CSS и кастомных обёрток; для внутреннего проекта важна скорость, а не уникальный дизайн.
- Redux Toolkit — один store с DevTools и предсказуемыми переходами. `tableSlice` удобно отлаживать по экшенам; middleware для WebSocket тривиален. RTK Query закрывает REST и кэш — отдельный TanStack Query не нужен.
- Zustand и shadcn/Tailwind — хорошие инструменты, но в этом проекте они требуют больше ручной сборки UI и разрозненных сторов.
**Цена.** Mantine — крупнее бандл и «свой взгляд» на компоненты; Redux — больше бойлерплейта, чем в Zustand. Для 3–4 разработчиков и 10 экранов это приемлемо.
**Альтернативы.** shadcn + Tailwind (больше свободы, больше ручной работы), Zustand (легче, но меньше структуры), MUI (тяжелее по стилю, Mantine ближе к «просто работает»).

### ADR-006. React Native + Expo, React Native Paper для mobile

**Решение.** Expo SDK 58, RN 0.88, Expo Router, React Native Paper.
**Почему.** Mantine не поддерживает React Native, поэтому для mobile берём Paper (Material) — стабильную библиотеку с готовыми компонентами; общими остаются протокол, Redux-слои и движки.
**Цена.** Два UI-кита (Mantine web, Paper mobile) — но общий дизайн-язык задаётся токенами и структурой экранов.
**Альтернативы.** Flutter — второй язык и дублирование протокола; Unity — избыточен для 2D-карт.

### ADR-007. Web — отдельный React SPA на Vite

**Решение.** Отдельное приложение `apps/web`: React 19 + Vite + React Router. Сборка — статические файлы, их раздаёт Node-процесс; API и WS — там же.
**Почему.** SSR/SEO не нужны, а Next ради 10 клиентских экранов — лишний слой. Vite проще, сборка быстрее, приложение можно вынести в отдельный репозиторий, не меняя остальное.
**Альтернативы.** Next.js — больше возможностей, но серверный рендеринг и его инфраструктура здесь не окупаются; CRA — устарел; Remix — требует сервер.

## 4. Структура монорепозитория

```
card-games/
├── apps/
│   ├── server/              # NestJS: REST + WS + игры + таймеры (один процесс)
│   ├── web/                 # отдельное приложение: React + Vite + Mantine + RTK
│   └── mobile/              # Expo, RN Paper, RTK
├── packages/
│   ├── domain/              # @cg/domain — чистые движки: blackjack, durak, holdem
│   ├── protocol/            # @cg/protocol — типы сообщений, Zod-схемы, коды ошибок
│   ├── client-core/         # @cg/client-core — RTK slices, WS-клиент, RTK Query API
│   ├── i18n/                # @cg/i18n — ресурсы RU/EN и типобезопасные ключи
│   └── config/              # общие tsconfig/eslint/biome/vitest-пресеты
├── infra/
│   └── docker-compose.yml   # app + postgres
├── docs/
└── .github/workflows/       # ci.yml, deploy.yml
```

Правила:
- `packages/domain` не импортирует ничего, кроме `protocol` и `rng`-утилит; никаких `pg`, `fs`, `process`.
- `client-core` не знает, web это или mobile — только RTK и WS.
- Границы проверяются Biome-правилами и code review; отдельный `dependency-cruiser` не нужен.

## 5. Что не берём и почему

| Технология | Почему нет |
|---|---|
| Redis | состояние в памяти, сессии в JWT; второй инстанс не планируется |
| NATS / Kafka | нет фоновых событий и воркеров |
| Kubernetes / Terraform / Helm | одна VM и Docker Compose; сложность не окупается |
| Микросервисы | 3–4 разработчика, одна БД, одна транзакция на раздачу |
| GraphQL | REST + WebSocket достаточны, проще кэш и отладка |
| Next.js | SSR/SEO не нужны; отдельный React SPA на Vite проще |
| MongoDB | PostgreSQL + JSONB покрывает гибкие поля |
| Stripe / StoreKit / Play Billing | нет монетизации |
| PostHog / ClickHouse / Grafana | нет продуктовой аналитики; хватает логов и админ-счётчиков |
| Sentry | опционально, включается при необходимости |
| IAP, пуши, App Store/Google Play | внутренние сборки |
| Unity / PixiJS | карты нормально рисуются DOM/CSS |
| Auth0 / Clerk / Keycloak | свой auth на 150 строк проще и бесплатен |
| Zustand / TanStack Query / shadcn / Tailwind | заменены на Redux Toolkit(+RTK Query) и Mantine |
